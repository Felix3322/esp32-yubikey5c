LibreFido 2.2.4 adds a dedicated M5Stack AtomS3U build for the user-presence
button issue reported in #3. Its button is GPIO41, active low, with a pull-up.
Generic ESP32-S3 builds keep GPIO0. Presence checks, debounce and the
release-before-another-confirmation rule are unchanged.

| Hardware | Standard image for initial flashing at `0x0` | Layout / button |
| --- | --- | --- |
| ESP32-S3 N16R8 / compatible 16 MB boards | `librefido-2.2.4-esp32s3-standard-full.bin` | 16 MB / GPIO0 |
| M5Stack AtomS3U (ESP32-S3FN8, 8 MB flash) | `librefido-2.2.4-atoms3u-4mb-standard-full.bin` | Existing 4 MB layout / GPIO41 |

The AtomS3U image uses the existing 4 MB layout: one profile and 256 KiB of
key storage. The generic image needs 16 MB; its partitions extend to 13 MiB
and cannot be used on AtomS3U. A native 8 MB layout has not been added.

For each board, the release includes a full image, an application image for
same-layout updates, and a ZIP with the separate flashing parts and build
metadata. Standard and hardened builds are included. Hardened builds require
the chip security provisioning described in `docs/PROVISIONING.md`; use
standard for normal bring-up.

For the AtomS3U reported in #3, use the full image from its ROM download mode:
the old GPIO0 build cannot authorize a button-confirmed in-app update.

```bash
python -m esptool --chip esp32s3 -p COM6 write-flash --flash-size 4MB 0x0 librefido-2.2.4-atoms3u-4mb-standard-full.bin
```

Replace `COM6` with the device port. On an AtomS3U already using the 2.2.2
4 MB image, this keeps the same storage layout; do not run `erase-flash` if
you want to keep its data. Do not switch between the 4 MB and 16 MB layouts
as an in-app update. Future AtomS3U updates must use the AtomS3U image to
keep GPIO41.

The CLI/GUI wheel includes the 2.2.3 PIV compatibility fix for cryptography 41.

```bash
python -m pip install "librefido_tools-2.2.4-py3-none-any.whl[gui]"
```

Validation: ESP-IDF 5.5.1 builds, firmware descriptors, resolved button
configuration, partition bounds, OTA slot sizes, packaged image contents,
and three host GPIO regression configurations. The regressions compile the
real ESP GPIO presence code and test debounce, the other board's GPIO,
release before reuse, timeout and cancellation without a device or keys.

**The new AtomS3U image still needs physical WebAuthn registration and
authentication testing.** No successful AtomS3U hardware test is claimed.

`SHA256SUMS` covers the release assets. An OpenPGP signature is not attached.
